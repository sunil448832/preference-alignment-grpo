# Preference Alignment on Qwen3-4B: RLVR GRPO

Companion project to the author's post-training study notes (a private document, referred to below as "the study
doc"; its GRPO/RLVR chapter and one-GPU recipe). Implements that recipe's final stage — GRPO with a verifiable Python
reward, no reward-model weights in the loop.

## Goal

Train Qwen3-4B-Instruct-2507 with GRPO where the reward comes from a plain Python function that checks whether
the model's math answer is correct — not a trained reward model. Show a real, visible before/after gap on
held-out problems.

*(Scope note: an earlier version of this plan also had an Experiment 1 — GRPO reward from a trained reward
model, built on on-policy preference pairs generated by the model itself. Dropped for now: RLVR only, and using
an existing dataset rather than generating one.)*

## Model

**Qwen3-4B-Instruct-2507**, NF4 (bitsandbytes) base + LoRA adapters on every linear layer
(`target_modules="all-linear"` — attention-only LoRA underperforms per the study doc's §8.6.1 findings).

Not a claim that a 4B model is "comparable to Sonnet 4" in general capability — no sub-7B model is. It's the
strongest currently-available open sub-7B instruct model, which is what matters for demonstrating the pipeline.

## Dataset — existing, not generated

**`PrimeIntellect/verifiable-math-problems`** (HF Hub, 777,457 rows) — confirmed via the HF datasets-server API
against the live dataset, not assumed. Columns: `source`, `task_type`, `prompt`, `gold_standard_solution`,
`verification_info`, `metadata`, `problem_id`. `verification_info` is a **string** holding a Python-dict repr,
e.g. `"{'ground_truth': '\\frac{13}{6}'}"` — needs `ast.literal_eval`, not JSON parsing (single quotes, not
valid JSON).

`source` breaks down as: `cn_k12` 261,323 · `synthetic_math` 167,872 · `orca_math` 153,314 · `olympiads` 97,078 ·
`synthetic_amc` 62,104 · `aops_forum` 16,877 · `math` 7,477 · `gsm8k` 7,342 · `amc_aime` 4,070 — this is
NuminaMath's per-example source breakdown. **`data/load_and_split.py` filters to `{olympiads, amc_aime,
synthetic_amc, aops_forum}`** (176,579 rows survive) — the competition-level subset, and explicitly excludes
`gsm8k` and `math`, which are the exact benchmarks Qwen decontaminates its training corpus against (see "why not
GSM8K/MATH directly" below); `cn_k12`/`orca_math`/`synthetic_math` are grade-school level and likely near-ceiling.
Correction to the dataset card's claim: multiple-choice framing is **not** fully dropped — some `synthetic_amc`
rows keep inline options (`A. 1  B. 3  C. 5 ...`) with a letter `ground_truth` (e.g. `'B'`). Not a problem for
`math_reward` (the options are in the prompt, so the letter is answerable and boxes/verifies fine), just don't
assume every row is a free-form numeric answer. `cn_k12`/`orca_math`/`synthetic_math` are grade-school level and
likely near-ceiling out of the box, so also excluded.

Why this over GSM8K/MATH directly: Qwen explicitly decontaminates its training corpus against GSM8K/MATH's exact
test sets, but the model is still tuned toward that *style* of problem and likely sits near ceiling zero-shot.
The competition-level subset above is harder and less likely to be saturated. It's still public data, so treat
"no contamination" as unverified — the Stage 1 pilot below is the actual check, not an assumption.

**Verifier — `math-verify`** (`pip install math-verify`, `huggingface/Math-Verify`): extracts the answer
(LaTeX/boxed/plain expression), converts to a SymPy-comparable form, checks equivalence against the gold answer.
This *is* the "Python code that gives reward if task succeeded" — no need to hand-write a parser.

**`reward_fn.py` — done, tested against real `train_pool.jsonl` rows** (not the naive version below — see file
for the actual implementation and why). Two things the naive `parse(completion)` approach gets wrong, found by
testing against real data rather than assuming the library "just works":
- Gold parsing: `parse(raw_ground_truth)` silently disagrees with `parse("\\boxed{" + raw_ground_truth + "}")`
  for expression-type answers (`"3n"`, `"n^3"`) — only matches for plain numbers. Must wrap gold in `\boxed{}`.
- Completion parsing: `math-verify`'s default extraction grabs **every** `\boxed{...}` in a completion as a set
  when there's more than one. A self-correcting completion ("first I guess `\boxed{5}`, wait, final answer
  `\boxed{11}`") parses as `{5, 11}` and fails `verify()` even when the final answer is correct. Fixed by
  manually extracting the **last** `\boxed{...}` (with proper brace-matching for nested LaTeX like
  `\boxed{\frac{13}{6}}`) before handing it to `math_verify.parse`.

```python
# reward_fn.py — see file for extract_last_boxed() and full implementation
def math_reward(completions, ground_truth, **kwargs) -> list[float]:
    rewards = []
    for completion, gold in zip(completions, ground_truth):
        boxed = extract_last_boxed(_completion_text(completion))
        if boxed is None:
            rewards.append(0.0)
            continue
        pred = parse(f"\\boxed{{{boxed}}}")
        gold_parsed = parse(f"\\boxed{{{gold}}}")
        rewards.append(1.0 if verify(gold_parsed, pred) else 0.0)
    return rewards
```

## Stage 1 — Pilot: measure baseline headroom

Before any training: sample ~500 problems from the dataset, run Qwen3-4B-Instruct-2507 zero-shot, score with
`math_reward`. This is the actual contamination/ceiling check (§ above) — run empirically, don't assume it.

- If baseline pass rate is already high (>80%): the set (or this difficulty slice of it) is saturated for this
  model — filter to a harder subset (the dataset spans difficulty; bucket by source/problem length as a proxy,
  or just keep the hardest-looking olympiad-style rows) and re-check.
- Target: baseline pass rate in **0.2–0.8** — the band where GRPO actually has gradient to work with (§7.3:
  zero-variance groups contribute nothing).
- Output: `eval/baseline_results.jsonl`, a written-down baseline pass rate to compare against post-training.

## Stage 2 — GRPO training

- `trl.GRPOTrainer(use_vllm=True)`, `reward_funcs=[math_reward]`.
- Prompts: the difficulty-filtered slice from Stage 1, held-out eval split carved out first and never trained on.
- Group size G=8, LoRA r=16, α=32, `target_modules=all-linear` (q/k/v/o/gate/up/down — see architecture note
  below), LR 1e-5, β=0 (no reference model — DAPO/Dr.GRPO default per §8.6.2; the KL leash exists to stop a policy
  exploiting a *learned* reward model's errors, and a verifier has none to exploit — turn β on (0.01–0.04) only
  if training shows collateral damage like format collapse or language mixing). r=16 is not a capacity need — an
  RL run over a few thousand episodes carries far fewer bits than even r=1 could hold (§8.6.1) — it's picked to
  match the range most `trl`/Unsloth GRPO examples assume, which keeps a first run easier to debug against
  known-good configs. Adapter is ~33M params (~0.8% of the 4.02B base, ~530MB at 16 bytes/param) — negligible
  next to vLLM's rollout KV cache, so there's no memory reason to go lower.
- Re-filter the training pool every few hundred steps to the 0.2–0.8 pass-rate band as the model improves
  (§8.6.3 Stage 3 guidance — a prompt the model has mastered stops contributing).

**Batch-size correction** (found reading `GRPOConfig`'s actual docstring while writing `train_grpo_rlvr.py` —
"batch=8 prompts × G=8" above was loose): trl has no single "prompts per step" field. It emerges from
`per_device_train_batch_size × gradient_accumulation_steps ÷ num_generations`. The script sets
`num_generations=8`, `per_device_train_batch_size=8` (the real forward/backward micro-batch — this is what the
GPU sizing table's "micro-batch 8" activation number actually corresponds to), `gradient_accumulation_steps=8` →
generation_batch_size = 64 sequences/rollout = 8 unique prompts × G=8, matching the sizing table below without
changing any of its numbers.

### GPU sizing (per_device_train_batch_size=8 × gradient_accumulation_steps=8 → 64 concurrent rollout sequences, seq_len=2048)

| component | formula | value |
|---|---|---|
| Base model (NF4) | 4.02e9 params × 4 bits | ~2.3 GB |
| LoRA r=16 + Adam state | 33M params × 16 bytes | ~0.53 GB |
| vLLM KV cache | 2×L×KV_dim×S×64×2B | ~18.0 GB |
| Training activations (grad checkpointing, micro-batch 8) | L×8×S×H×2B | ~3.0 GB |
| LM-head log-probs (fused/chunked, micro-batch 8) | vs. ~5GB naive | ~0.5–1 GB |
| **Total (fused log-probs)** | | **~24–25 GB** — fits a 40GB GPU comfortably |
| Total (naive, unfused logits) | | ~29 GB — still fits 40GB, tighter |

Confirm the training script uses a fused/chunked log-prob kernel (Liger-Kernel, Unsloth, or equivalent) rather
than materializing full `batch×seq×vocab` logits — that's the single config choice most likely to blow the
budget, given Qwen3's 151,936-token vocab. KV cache (the largest term) scales with `batch_prompts × G ×
completion_length` — the lever to pull if this needs to shrink further. Training-side activations/logits are
controlled independently via micro-batch size + gradient accumulation, not by total rollout batch size.

**Target instance: 40GB GPU minimum (A100-40GB), 48GB preferred for the first run.** The ~24–29GB core estimate
doesn't include CUDA context/allocator fragmentation or vLLM's own reservation overhead. The earlier open
question (does colocated vLLM share the base weights or load a second copy?) is now answered from `trl`'s
source (`generation/vllm_generation.py`): it loads a **second copy, but bitsandbytes-quantized** — it detects
`Linear4bit` modules and starts vLLM with `quantization="bitsandbytes"`, so the copy is ~2.5GB, not 8GB. vLLM's
total slice is set by `vllm_gpu_memory_utilization=0.4` (16GB on a 40GB card: weights + ~13GB KV cache; the 18GB
in the table above is what 64 full-length sequences need at once, so vLLM will schedule them in ~2 waves). Each
weight sync merges the adapter into the 4-bit base (lossy re-quantisation — fine for rollouts, and why the
final adapter is saved unmerged).

### Compute cost estimate

Revised 2026-09-18 for cap 4096, micro-batch 4, NF4 training, colocated bnb vLLM at 0.4. Anchored on one
measurement (A10G, vLLM bf16: 20 prompts to mean ~1.5K tokens in 50 s, ~25 ms per decode step at ~20 concurrent)
scaled by the A100's 2.6x bandwidth / 5x bf16 compute. The earlier 35 s/step figure assumed 10K tok/s from vLLM
and a 2048 cap; it was ~5x optimistic.

Per step (8 prompts x G=8 = 64 sequences, ~160K generated tokens at mean ~2.5K):
- rollout: ~11 ms/decode step, ~29 sequences in flight in the 16GB slice -> ~2.5K tok/s -> **60-90 s**
  (lower bound ~45 s = the longest 4096-token sequence)
- training: ~300K padded token positions x 5 forward-equivalents (old logprobs, forward, checkpoint recompute,
  backward x2) = ~12 PFLOP at 100-125 TFLOPS effective (NF4 dequant + LoRA) -> **100-120 s**
- adapter save + vLLM LoRA reload + chunked log-softmax: a few seconds
- **~3-3.5 min/step** at the mean length; **~3.5-4 min/step** if every completion runs to the 4096 cap
  (262K tokens, ~19 full-length sequences in flight -> rollout ~110-130 s; training already assumes padding
  to 4722, so it is unchanged). Early steps sit near the cap-bound case; it eases as the policy learns to finish.

| steps | wall time (mean length / all at cap) | A100-40GB on-demand (~$1.5-2/hr) |
|---|---|---|
| 200 | ~10-12 hr / ~12-14 hr | ~$15-28 |
| 500 | ~25-30 hr / ~30-35 hr | ~$40-70 |

A10G-24GB (sleep-mode config): training phase ~5x slower, rollout ~2.5x slower -> ~11-13 min/step, ~100 hr for
500 steps. Sanity runs and short experiments only.

Levers: training is ~2/3 of the step and NF4 dequant is a large part of it -- bf16 LoRA on unquantized weights
fits the 40GB card alongside vLLM at 0.4 and should cut the training phase; measure both in the first hour. Step
count is the other lever: checkpoints land every 100 steps, plan for 200-300 unless the reward curve is still
rising. Rollout time floors at the longest sequence and shrinks as the policy learns to finish sooner.
Budget 2-3x the clean-run number for debugging/restarts. Re-time one real step on the pod and replace this table.

**π_old / π_θ restructure (2026-09-15)** — the loop now has DeepSeekMath's actual GRPO shape (Algorithm 1):
- `π_old(o_t)` and `π_θ(o_t)` are the *same computation* — `(question, response-so-far)` → policy → softmax over
  the vocab → the entry for the token actually sampled — at two moments. `logp_old` is computed **once per
  rollout batch**, right after generation, under `no_grad`, with the weights that generated it, and stored.
  `logp` is recomputed from the live weights on every gradient step.
- `NUM_ITERATIONS` (μ) gradient steps run against that stored `logp_old`. At μ=1 (default, same as `trl`'s
  `num_iterations=1`) the weights haven't moved on the only step, so the ratio is exactly 1 and the clip is
  inactive; at μ>1 steps 2..μ see moved weights, ratio≠1, clip active. `train_grpo_rlvr.py` sets
  `num_iterations=1` explicitly for the same reason.
- **Dropout off in both scripts** (`lora_dropout=0.0`; `disable_dropout=True` in `GRPOConfig`). Measured: with a
  trained adapter and *unchanged* weights, dropout alone spread the ratio over 0.80–1.33 between two forward
  calls. That is noise the clip would act on as if it were policy drift. (This only shows up once the adapter
  has trained — `peft` zero-initialises `lora_B`, so a fresh adapter's LoRA path outputs 0 regardless of dropout,
  which hid it in the first test.)
- Earlier version used `logp_old = logp.detach()`; numerically identical at μ=1, but structurally wrong for μ>1
  and it made the "old" policy look like a no-op. Replaced.

**Training-readiness review (2026-09-16)** — every file re-read, every suspicion checked against the real
model config / library source / data rather than assumed. Fixed:
- **Sampling distribution mismatch (real correctness bug).** The model's `generation_config.json` ships
  `temperature=0.7, top_k=20, top_p=0.8`. `rollout()` overrode temperature and top_p but not `top_k`, so tokens
  were sampled from a top-20-truncated distribution while `logp_old` was computed from the full softmax — the
  ratio would have compared two different policies. Now `top_k=0` explicitly. (`trl` defaults `top_k=0`, so the
  vLLM path was already correct.)
- **Completion mask.** `generation_config` has two EOS ids, `[151645 <|im_end|>, 151643 <|endoftext|>]`, and
  the second is also the pad id — so `mask = ids != pad` would drop a legitimate `<|endoftext|>` EOS. Replaced
  with "1 up to and including the first EOS, 0 after" (`completion_mask_from_ids`), and the attention mask now
  zeroes post-EOS padding too.
- **Logits memory.** `sequence_logprobs` materialised full-sequence logits and an fp32 `log_softmax` copy: for
  micro-batch 8 × ~2.3K positions × 151,936 vocab that is ~5GB bf16 + ~11GB fp32 + ~11GB output, per chunk. Now
  uses `logits_to_keep=completion_len+1` (prompt logits never built) and a per-row `logsumexp`, the same shape
  as `trl`'s `selective_log_softmax`. Verified equal to the naive computation to 2e-6.
- **Dropped `prepare_model_for_kbit_training`** in the pure-PyTorch script: it casts *every* non-quantised

**Adaptive sampling (2026-09-20).** The 15-step 2-prompt run showed why most steps carried nothing: of 30 groups,
17 were all-wrong, 8 all-correct, 5 mixed -- the pool is bimodal for this policy, so raising G alone would not help
(a p=0 or p=1 prompt is zero-variance at any G). Implemented in train_grpo_pytorch.py (`collect_groups`): G rollouts
per prompt; prompts whose G all score 0 are re-sampled together in rounds of G (one vLLM call per round) until a
success appears or `cfg.batch.max_rollouts_per_prompt` (24) is spent; the training group is then the successes (up
to G-1) plus a random fill of failures, still G wide so the loop is unchanged. Prompts that exhaust the budget are
parked for `park_steps` (100) -- only a changed policy can change that outcome -- and prompts solved G/G with zero
variance `park_after_all_correct` (2) times in a row are parked too (with the length penalty on, all-correct groups
usually have variance and are not parked). Parked/streak state is checkpointed and restored; `draw_prompts` uses
the torch RNG so resume stays exact. Bias to keep in mind: a rescued 1-in-24 prompt is presented as 1-in-8; direction
right, magnitude generous. Cost lands on p~0 prompts (unwinnable labels, figure references) once per park cycle --
label cleaning removes most of them up front. The HF backend now goes through the same path (`hf_sample` ->
`collect_groups` -> `assemble_batch`); `rollout()`/`rollout_vllm()` are gone. Per-step log fields: retried_prompts,
rescued_prompts, exhausted_prompts, extra_rollouts, retry_rounds, parked_total. Verified on CPU: fixed group size,
batched retry rounds, budget==G disables, rescue rate for a p=0.15 prompt 70% -> 100% (theory 73% -> 98%), parking
and un-parking in the loop, bit-exact resume including parked state, HF sampler path on the tiny model.
Recommendation for the next real run: length penalty back on (converts the ~27% all-correct groups into signal).

**Clip failed rollouts to the longest correct one (2026-09-20).** `cfg.batch.clip_negatives_to_positive` (True): in a
group with at least one correct rollout, failed rollouts are truncated to the longest correct one's length after
scoring. Token-level this equals masking the tail out of the loss (causal log-probs of the prefix don't depend on
it): the negative push lands on the prefix where the correct answer had already finished, the tail where the model
was lost -- mostly gradient noise, DAPO's overlong argument -- is dropped, and the padded micro-batches shrink
(a group with two 600-token successes and six 4096-token failures trains on ~8x600 instead of ~8x4096 tokens).
Rollout metrics (mean tokens, at cap) are recorded before clipping; the log adds `train_tokens` and
`clipped_tokens`. Groups without a success are untouched. Verified on CPU (helper + full step with the flag on/off).
Bias to watch: the negative mass concentrates on the failures' prefixes, which may contain sound early reasoning --
compare eval pass rate with the flag off if the curve looks worse than expected.

step 0 (paired baseline of the untrained adapter), after every `every` completed steps (inside the next step's
rollout window, engine awake + synced; eval time excluded from rollout_s), and once more after the last step.

number is `evaluate.py` on all 500. Smoke mode evals every 2 steps on 20 rows. Verified on CPU: schedule
[0, 2, 4, final], engine awake at eval, no duplicate after interrupt+resume, HF greedy path deterministic.
